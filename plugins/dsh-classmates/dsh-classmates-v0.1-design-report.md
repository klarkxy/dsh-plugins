## 1. 最终决策摘要

**做一个独立、轻量的 DSH 插件：用户配置可用的专业队友，主 Agent 决定是否使用、使用谁、如何分工，官方 Agent Teams 负责实际协作。**

首版压缩为：**一个仓库、一个可安装 bundle、一张配置页面、两个模型工具、三个可编辑示例角色。**

唯一需要首先证明的产品闭环是：

> 用户给一个角色绑定模型、思考强度、职责和工作指令；主 Agent 发现这个角色并创建它；创建出的成员属于官方 Team，而且从第一个请求到重试、冷恢复，都按这份配置工作。

不做另一个 Harness，不做组队器，不做流程设计器。首版不依赖 `dsh-editor`，也不以 `dsh-spaces` 的专用接口为前提。公开支持面先限于一个经过验收的 DSH Web 宿主版本。

### 1.1 首发必须有

| 能力 | v0.1 决策 |
|---|---|
| 角色库 | 新建、编辑、删除、启用/停用 |
| 每角色设置 | 名称、职责说明、模型路由、思考强度、工作指令 |
| 主控发现 | 按需读取启用且配置有效的角色目录 |
| 主控调用 | 按角色定义创建真正的官方 teammate |
| 专业化执行 | 模型与提示词只作用于对应成员，不改主控 |
| 恢复一致性 | 已创建成员使用创建时快照，不随模板编辑漂移 |
| 上手示例 | Researcher、Writer、Verifier 三个未绑定模型的示例 |
| 发布支撑 | 精确兼容说明、干净安装验收、真实演示、脱敏反馈模板 |

### 1.2 首发明确不做

不做 Team Recipe、Fusion/Swarm/Editorial 模式选择、固定 DAG、自动路由模型、角色评分、角色市场、远程导入、工作流可视化、第二套任务库、第二套邮箱、第二套 Session 管理、成本仪表盘、跨空间同步、A2A、worktree、工具权限编辑器、自动发布、Editor 正文采用流程或热迁移框架。

**砍功能，而不是砍模型绑定正确性、恢复一致性和安装可靠性。**

## 2. 本轮研究带来的关键修正

### 2.1 不把上游 PR 合入作为首发前提

官方 `dsh-v0.1.7-rc.2` 的 Team 创建实现仍只向 continuable 层传递任务和父 Agent，没有在该调用中转发逐成员 `agentOptions`、`persona`、`toolFilter`。因此，不能假装给 `spawn_teammate` 多传几个 JSON 字段就能生效。[S2]

但同一标签的核心包公开导出了 `installModelSelection()`。该函数将 Agent 作用域内的模型选择同时接到提示词组装和请求路由，按步骤捕获选择；未指定 effort 时会清除继承的 effort，使用所选模型的默认行为。[S3]

**定稿路线：优先使用公开的模型选择与作用域扩展点，薄接入官方 Team，而不是先维护一个 DSH fork。** 这是一条经源码支持的实施路线，不是已完成集成验证。第 12 节的 P0 实验必须先证明首请求时序和恢复成立。

若 P0 证明某个必要钩子无法满足契约，才集中提出最小上游扩展。不要同时开发两套后端，不要悄悄降级为一次性 subagent，更不要把一个只能保存配置的页面当作可用版本发布。

### 2.2 官方 Team 是协作底座，不是自动完成业务的工作流引擎

官方工具提供创建、消息、等待、中断及共享任务操作；权限由 Team 服务检查，成员是否正在运行与任务是否完成不是一回事。工具的固定策略要求用户明确请求团队协作，普通任务不应自动委派。[S4]

因此，用户说“主 Agent 自己组队”应被解释为：**在用户授权的协作任务里，主 Agent 自己决定成员和过程**，而不是安装插件后所有对话自动多开模型。

### 2.3 市场不是空白，差异不能写成“第一个”

本轮发现 `lolkda/dsh-agent-team-model-pin` 已经提供 Team 模型与 effort 配置。读取到的 README 标示当前 1.3.0，并描述复用公开 `installModelSelection()`、原生设置和模型目录；这是作者的实现与测试说明，本报告没有复跑其验证。[S8]

TeamFlow 则公开提供多阶段研发流水线与工作台，解决的是流程和交付治理问题。[S9]

我们的切口是：**每个角色独立定义，主控按任务选择，保留官方协作体验，不要求用户设计组织或流水线。** 不宣称市场唯一，也不预先宣称比其他插件快或省钱。

### 2.4 角色目录比“自动组队算法”更适合当前目标

Claude Code 和 Gemini CLI 的文档均强调 description 对专家选择的重要性；Claude 还明确建议把详细工作指令移入只在子代理运行时加载的提示词。OpenCode 已将 description、prompt、model 和 provider-specific 参数分开配置。[S10][S11][S12]

本项目借鉴这种分离，不照搬整个 Harness：**description 给主控判断，instructions 给成员执行，model binding 给宿主解析。**

## 3. 定位、用户与成功标准

### 3.1 一句话定位

**Custom specialists for DSH Agent Teams. You define the teammates; your main agent decides how to use them.**

中文：**给 DSH 配置自己的专业队友，具体怎么协作由主 Agent 决定。**

### 3.2 首批用户

已经使用 DSH Web、已有可用模型路由、希望为不同专业角色配置不同模型或提示词的用户。不把“首次注册模型供应商、申请 API Key、学习工作流编排”塞进插件引导。

### 3.3 首版验证什么

验证三个问题：用户能否迅速配出角色；主控能否恰当地发现和使用它；真实成员的执行是否与用户配置一致。

暂不验证“哪种团队结构最优”“多 Agent 是否普遍胜过单 Agent”。这些需要同任务、同验收标准的对照，不应由一次展示推导。

### 3.4 正常使用不应被接管

安装和打开页面不触发推理；保存模板不创建成员；没有有效启用角色时，不挂载本插件的模型工具。启用角色后只增加小的工具与发现提示开销，**不能承诺零 token 开销**。目录为空时不挂载发现/创建工具，但恢复已有实例所需的绑定监听仍保留，不能因模板被删空而丢弃旧实例配置。

首版沿用官方明确请求协作的使用方式。示例入口为“使用我的 Classmates 帮我研究这个问题”。这只是自然语言入口，不是固定流程或额外调度器。官方 prompt policy 不是安全授权系统，实际工具执行和审批仍由宿主负责。[S4]

## 4. 产品边界：只定义“人”，不定义“组织”

| 主体 | 唯一责任 |
|---|---|
| 用户 | 角色职责、模型、effort、工作指令、是否可用 |
| 主 Agent | 是否需要协作、选择谁、任务拆分、消息协调、接受结果 |
| dsh-classmates | 角色定义、发现、校验、创建绑定、作用域配置与一致性 |
| 官方 Agent Teams | 成员身份、消息、任务、等待/中断、Session 生命周期和恢复 |
| DSH 宿主 | 凭据、模型目录、实际请求、工具、沙箱、审批、持久会话与基础 UI |
| 未来领域插件 | 写作提案、作者采用、代码验收等业务语义 |

Fusion 的 Brief/Report/Review 和作者确认不因本项目而消失，也不在本次迁移。新项目不重写现有 Fusion 或 Editor。

## 5. 用户体验：一张页面完成配置

### 5.1 页面结构

桌面可用“角色列表 + 编辑区域”，窄屏用“列表页进入编辑页”。复用宿主组件、目录与配置保存能力，不接管主模型选择器，不复制官方 Team 面板。

列表只显示：名称、简短职责、模型与 effort、启用/未配置/配置错误。运行中成员与已保存模板不是同一个对象，不能在模板卡片上伪造“正在运行”的状态。

编辑表单只包含：

| 字段 | 给用户的解释 |
|---|---|
| 名称 | 在角色目录里叫什么 |
| 职责说明 | 主 Agent 在什么情况下应考虑找它，以及不负责什么 |
| 模型 | 从宿主已配置的 provider/model 中选择 |
| 思考强度 | 仅展示该模型支持的档位，另有“模型默认” |
| 工作指令 | 这个成员执行任务时应该遵守的具体方法与输出要求 |
| 启用 | 是否允许主控通过本插件创建此角色 |

模型参数不扩展到 temperature、top-p、输出上限、备用路由等整套高级面板。用户本次明确需要的 model + reasoning 是首发边界。

### 5.2 模型设置语义

首版采用**显式绑定**，不做持续“跟随主 Agent”、自动选模或 fallback。可以提供“一次复制当前主模型”的表单便捷操作，但保存结果必须是明确路由，而不是动态继承规则。

切换模型时清除不再适用的 effort，回到“模型默认”，要求用户重新选择。模型没有可用 effort 档位时禁用选择控件并解释原因。不要把所有模型统一硬映射到 low/medium/high。

保存时校验目录和字段；创建时再校验一次，防止供应商配置已经改变。目录或模型不存在、effort 非法时明确报错，不静默换到主控模型。[S3][S11]

“模型默认”意味着由所选路由和适配器决定，不保证未来供应商默认值永不改变；需要稳定档位的用户应选择明确 effort。

### 5.3 三步上手

选择一个示例角色，绑定模型并保存启用，在普通对话明确要求使用 Classmates。之后主控如何组合、是否并行、是否追加成员，都不由页面配置。

页面附一个可复制的演示请求，而不是启动后台测试或自动发送消息。

## 6. 最小数据模型

以下为**本项目拟新增的数据契约**，不是声称 DSH 已有同名接口。

```ts
interface ClassmateDefinition {
  schemaVersion: 1;
  id: string;                 // 自动生成或由用户确认的稳定 slug
  revision: number;           // 宿主保存成功后递增
  name: string;               // 人类显示名，可使用中文
  description: string;        // 给主控看的简短职责说明
  instructions: string;       // 给成员的长期工作指令，按纯文本处理
  enabled: boolean;
  model: {
    provider: string;         // 宿主已注册的 LLM provider
    id: string;               // provider 所属的 model id
    reasoningEffort?: string; // 缺省表示该模型默认
  } | null;                  // 未配置草稿必须保持 disabled
}
```

不存 API Key、供应商登录信息或另一份模型目录。模型目录能力说明与凭据均由 DSH 提供。

`id` 与官方 Team 的成员 `name` 分开：同一个 researcher 定义可以被主控创建为不同任务中的多个真实成员；主控不能通过相似名称冒充某个已绑定角色。

配置只做单一 profile 作用域，不增加全局、空间、项目、团队、会话五级继承。schemaVersion 只支持 v1；未知版本报错，不为首版建迁移框架。

### 6.1 模板和实例快照必须分开

模板可编辑；已经创建的成员使用创建时快照。快照最少保存：宿主 profile 标识、Lead Session ID、目标成员名、角色 id/revision、完整解析后的模型选择、工作指令、首任务摘要哈希及快照校验值。

它是插件拥有的**配置绑定记录**，不是第二套 roster。不得写入运行状态、任务状态、收件箱、聊天历史、token 账本或任务产物。

模板删除或停用只阻止后续创建，不自动停止已存在的成员。UI 明示“修改应用于新创建的成员”。首版不支持对现有成员热换模型或指令。

## 7. 模型侧接口：只新增两个工具

### 7.1 `classmates_list`

只向真实的 Team Lead 暴露，用于获取已启用且配置有效的角色。返回 id、revision、显示名、职责和选定模型摘要；不返回密钥，不返回完整 instructions，不列出全部未启用示例。

主控系统提示只追加一段很短的说明：用户请求协作时可查询 Classmates；有匹配角色再使用；没有合适角色可以自己完成。不把全量目录、六套 persona 或复杂用人规则塞进每轮上下文。

### 7.2 `classmates_spawn`

拟议输入：

```json
{
  "classmate_id": "researcher",
  "revision": 3,
  "name": "researcher-background",
  "task": "查找这个问题所需的背景材料，返回来源和不确定性。"
}
```

处理器检查真实 Lead 身份、启用状态、配置 revision、成员名合法性和模型可用性。LLM 不传任意 provider、effort 或 instructions 覆盖已批准的角色配置。

revision 过期时要求重新读取目录，不能默默采用刚被别人修改的新配置。创建成功返回官方成员 target，以及角色 id/revision、选定路由和原生创建回执。

**“选定配置”与“已观察到真实请求”分别表示。** 第一张回执不能凭空宣称已向指定供应商发送成功；真实观察来自最终请求配置，而非模型自述。

### 7.3 后续协作全部复用官方工具

成员之间通过官方 `send_message` 通信，任务使用官方 task 工具，等待与中断也保持原样。本插件不增加 `classmates_message`、`classmates_task` 或自定义调度 loop。

保留官方 `spawn_teammate` 作为创建普通成员的入口。只有通过 `classmates_spawn` 创建并具有本插件绑定标识的成员，才承诺使用角色配置。目录引导主控选择正确工具，不通过同名覆盖制造安装顺序依赖。

只有 Lead 创建成员；其他成员可以请求 Lead 召集某个专业角色，不通过本插件递归扩张团队。继续服从宿主现有的成员与执行限制，不新增一套并发调度器。[S4]

## 8. 技术接入：公开扩展点，不重造 Team

### 8.1 总体结构

```text
用户配置页面
    ↓
ClassmateDefinition + 配置校验
    ↓
classmates_list / classmates_spawn
    ↓
官方 ctx.agentTeams.spawnTeammate
    ↓
官方 continuable teammate
    ├─ 本插件的精确成员绑定快照
    ├─ Agent 作用域模型选择与工作指令
    └─ 官方消息、任务、恢复与 UI
```

### 8.2 推荐实现方式

**第一步：建立明确的来源标识。** 注册一个插件专用的 fresh subagent provider，例如 `classmates-spawn`。它的 continuable preparation 只返回空的 seed 贡献，真实创建和后续运行仍由官方 continuation manager 拥有。普通 one-shot 路径不对外使用。

官方 provider 契约明确说明：`prepareContinuable()` 返回数据，不拥有 Agent、执行、恢复或销毁；其 `ContinuableCreateSpec` 只有可选 seed。这条扩展点可以标识创建来源，但**不能用来假装传递 model/persona**。[S5][S6]

**第二步：先保存不可变绑定，再调用官方创建。** 以 profile + Lead Session + 目标成员名为键保存快照。只接受插件自己的可信写入；文件路径不直接拼接任意用户字符串。

调用官方 `ctx.agentTeams.spawnTeammate()`，使用 `provider: classmates-spawn`、`context: fresh` 和合法任务内容。不猴子补丁 `spawnTeammate`，不直接调用子代理来伪装 roster 成员，不改 shipped preset。

**第三步：在成员的首次组装前安装作用域配置。** 根据官方 durable descriptor、Team membership、专用 provider 标识和绑定快照联合识别成员；不能仅凭显示名识别。官方 roster 在创建前持久记录 provisioning 成员，并可识别 provisioning 或 active 的真实成员，为此提供了源码依据。[S2]

在该成员作用域安装独立的 `ModelSelectionRef` 与 `installModelSelection()`，将用户 instructions 注册为独立、纯文本的作用域提示节。使用本插件命名空间，不替换宿主 persona、安全政策或 Team identity 指导，不把 task 当作系统权限。

**第四步：每次恢复重新装配。** 新 Activation 根据原始快照重新安装同一模型选择和提示节，不重新读取最新模板来改变旧成员。

这四步仍需要 P0 实验验证事件顺序，尤其是插件监听安装必须先于第一个模型请求。不能把“监听了 agent/created”本身当作时序正确的证明。

### 8.3 为什么不只在最后一刻改请求字段

仅修改 `agent/request` 的 provider/model 可能让模型在提示中看到 A，却实际请求 B。官方 helper 处理了组装与路由的联动，应优先复用。[S3]

各成员必须持有独立的选择对象，不能修改全局默认或复用可变对象导致并行串模型。绑定后保持对象不可变，模板变化只影响新实例。

不再增加自研“模型智能路由服务”。所需模型验证调用宿主能力，发送模型请求仍完全属于 DSH。

### 8.4 兼容冲突

首版不承诺与另一个 Team model-pin/全局请求重写插件同时控制同一成员。检测到可确认的冲突时明确提示先关闭另一条绑定；安装测试只支持写明的标准组成。

最终请求的路由与绑定不一致时，在本插件能够检查的请求边界失败，不把错误路由标成成功。不声称能阻止任意第三方在更晚层私自改写请求。

官方某些 roster 视图仍从 `agent.options` 读取模型信息；这不等于最终请求路由。[S2] 首版以实际请求记录为运行证据，不以一个下拉框或 roster 文本证明绑定成功。无需为此复制整个 Team 面板。

## 9. 存储、失败与恢复的最小合同

### 9.1 两类数据，禁止扩展成业务数据库

角色定义通过宿主原生插件配置保存；实例绑定存在宿主当前 profile 的插件私有数据目录，以原子写入的 JSON 文件或已有等价持久存储保存。不写进用户项目仓库，不自动改 AGENTS.md、gitignore 或正文。

本报告使用 `<ProfileState>` 表示宿主认可的数据根，不把它误写成所有安装都相同的硬编码路径。数据目录解析与写权限需在真实宿主安装验收中确认。

实例绑定不复制官方记录的 child 状态，官方 roster 是身份和生命周期的唯一权威。

### 9.2 创建竞争与重复调用

同一 Lead + name 的插件创建操作串行化，并用快照/任务摘要判断重复请求。官方 Team 自己执行名称唯一性检查。[S2]

若调用结果丢失而成员已存在，只有身份标识、原快照和首任务摘要一致时，才返回已有成员回执，不再次发送任务。内容不一致则报名称冲突。不同 name 表示新的创建意图，不承诺自动识别语义重复。

如果绑定已保存但尚无官方成员，它只是未被采用的配置记录，不自动恢复成任务。确认没有对应 roster 成员后可以清理，不能自己发明 provisioning/running/done 状态机。

### 9.3 故障必须可见

以下情况不得退回主模型继续跑：绑定缺失或损坏、角色配置无效、模型不存在、非法 effort、首请求绑定未完成、恢复后的作用域装配失败、可确认的路由冲突。

模型超时或供应商错误仍由宿主报告和重试；插件不加自己的自动换模型链。

### 9.4 停用、删除、卸载

停用/删除模板不终止已创建成员；用户通过官方 Team 中断与会话控制管理它们。已有绑定继续存在，使模板删除后的旧成员仍可按原配置恢复。

卸载插件前应结束相关 Team 工作。v0.1 **不支持插件缺席时继续恢复 Classmate 的自定义行为**，也不承诺热卸载后仍替旧成员守住路由。官方 continuation 可以不依赖原 provider 持续注册，故“移除 provider”不能当作永久停机开关。[S5]

这一限制应写入设置页和 README。重新安装后保留的数据可用于正常恢复；不自动删除用户的原生 Session。若需要插件缺席也能保证的持久配置或强停用语义，再推动原生 descriptor 扩展。

## 10. 安全、上下文与能力边界

### 10.1 首版只用 fresh

不提供 fork 切换、不复制主控整段历史，只传当前任务需要的材料。但 fresh 只表示不复制父会话 transcript，不保证共享文件、项目注入或工具不可见。[S7]

不宣传“Writer 不可能知道秘密”或“事实核验员天然独立无偏”。信息边界与验证质量必须另行验证。

### 10.2 不做权限编辑器，但必须说明真实权限

v0.1 使用测试过的宿主 teammate 工具组成与原生审批/沙箱，不自动安装搜索、浏览器或 shell 工具，不新增权限豁免。

官方 in-process child 的工具作用域不会自动导入父级工具限制，所以不能把“与父 Agent 相同权限”写成未经验证的保证。[S7] 在受限 preset（尤其写作或敏感工作区）中，未通过子成员权限验收前不要宣称兼容。

示例提示中的“只报告，不修改”是行为指令，不是沙箱。首版不自称提供逐角色强制只读。后续权限 UI 必须对接可实际执行的 tool restriction，而不是几个表面复选框。

### 10.3 工具能力不等于模型能力

Researcher 能否上网取决于宿主提供的工具和许可，不是换一个模型就获得浏览器。模型目录只用于解析模型与 effort 等受支持参数，不替用户自动开通外部服务。

缺少必要工具时，角色应报告限制，不伪造搜索或证据。页面可显示宿主工具前提说明，但不新增“能力评分引擎”。

### 10.4 提示词与凭据

用户指令作为纯文本，不执行代码、不解释任意模板表达式。主控可读角色 description，但没有修改用户角色库的模型工具。

插件不保存 API Key，不增加外传遥测；用户选定的模型供应商仍会按宿主的正常调用接收任务内容。不要把“不新增遥测”宣传成“所有数据永不离开本机”。

## 11. 三个示例角色，全部可改

预置的是定义，不是运行成员；初始 `model: null`、`enabled: false`。用户选好模型后才能启用。不要预绑特定商业型号，不假定某个模型永远适合写作或核验。

### 11.1 Researcher：资料调查

**description**：负责外部资料调查和来源整理。在任务缺少背景、当前事实或可引用材料时使用；不负责最终正文或无证据的事实裁定。

**instructions 建议正文**：

> 根据收到的问题收集有关材料，优先使用可核查的一手来源。区分来源明确陈述、你的推断和尚未确认的信息。返回简短发现、可访问的来源标识、适用日期或范围、冲突与未知项。不要把没读过的来源当作已核实证据。没有可用检索工具时说明限制并向 Lead 请求处理。需要别的成员协助时使用官方 Team 消息，不另行建立团队。

### 11.2 Writer：内容写作

**description**：根据目标、读者、风格要求和已提供材料生成或修改内容。资料足够、需要形成正文候选时使用；不把创作补全冒充已核实事实。

**instructions 建议正文**：

> 依据任务目标和现有材料写作，保持用户要求的语言、结构和风格。事实信息不足时标注缺口，向 Lead 或有关成员询问，不自行编造出处。返回正文候选及需要用户或 Lead 决定的事项。不得仅凭本角色身份认定已有发布或正文覆盖授权；涉及工具写入时服从宿主审批和当前任务授权。

### 11.3 Verifier：内容核实

**description**：独立检查已有结论或正文中的可核查主张，寻找证据缺口、来源不支持和时间范围错误；不负责重写整篇文章。

**instructions 建议正文**：

> 先识别待核实主张，再检查证据是否真正支持它。不要因为另一成员说“已验证”就接受。区分有支持、证据不足、相互冲突和无法核实，说明理由与范围。允许结论保持不确定。工具不足时明确说明未完成核实。返回主张、证据、判断、建议修正；这些是可读报告要求，不是程序自动批准交付的质量门禁。

三个示例不组成固定流程。纯润色可以只用 Writer；研究问题可以只用 Researcher；有必要时才让 Verifier 加入，全部由主控决定。

## 12. 实施顺序：先证明核心，再做页面

### P0：最小技术证明，优先级最高

在独立的、精确版本 DSH Web 测试 profile 内，不依赖 Editor：通过原生 Team 创建带来源标识的 continuable 成员，使用公开 helper 安装模型选择和作用域指令。

捕获它的**第一个最终请求**，确认 model/provider/effort 和提示节正确，主控不变；再验证重试和一次冷恢复。这一关不过，不扩大 UI 和模板工作。

并行核对打包依赖边界：宿主核心 SDK 由宿主提供，不作为普通运行时 dependencies 再装一份。社区已有重复核心 SDK 导致全局/作用域注册冲突的记录，可作为必须回归的具体风险，而不是把开发目录能跑当成安装成功。[S8]

### P1：角色配置与创建闭环

完成 v1 schema、配置保存、模型校验、实例快照、两个工具和三份示例。先用测试调用或配置文件验证，不等页面完成。

### P2：一张可用页面

复用原生配置和模型目录，完成列表、编辑、保存错误与启用状态；默认只在新创建成员上生效。保持手机可操作，不开发新导航框架或团队工作台。

### P3：打包、验收和公开材料

从最终 `.tgz` 在干净 profile 安装；真实运行示例，核对卸载限制，录制真实过程。发布 alpha 的前提是第 13 节通过，不是截图做好。

所有顺序是实施依赖，不是工期承诺。首发阶段不将新功能插入当前闭环；影响核心的缺陷优先于扩展。

## 13. 发布硬门槛

以下全部是**待执行验收项**。本报告没有把它们标记为通过。

| 场景 | 必须看到的证据 |
|---|---|
| 干净安装 | 最终 tgz 在指定 DSH Web profile 加载 Host 与 Client，无第二份核心 SDK |
| 普通使用 | 未启用角色或未请求协作时不创建成员；主控配置不被重写 |
| 保存校验 | 缺模型、非法 effort、revision 冲突时不伪装保存成功 |
| 首请求绑定 | 两名成员的第一个请求分别携带各自 provider/model/effort，而不是先用主控模型跑一轮 |
| 思考默认 | 切换目标模型且使用默认时，原模型的 effort 不残留 |
| 并发隔离 | 两个成员并行启动，选择对象和指令不串到另一成员 |
| 指令作用域 | 主控没有被注入成员长指令；成员首次请求及恢复后都有正确指令 |
| 原生协作 | 成员真正出现在官方 roster，至少完成一次直接消息往返和共享任务操作 |
| 重试 | 同一步重试保持已冻结路由，不受设置页中途编辑影响 |
| 冷恢复 | 重启并恢复后仍使用旧实例快照，即便对应模板后来被编辑或删除 |
| 重复创建 | 同名同快照的失联重试不重复创建、不重复下发任务；不一致时报冲突 |
| 错误暴露 | 绑定丢失、模型不可用、装配失败时不悄悄退回主模型 |
| 停用与卸载 | 普通主会话保持可用；已创建成员与插件缺席恢复的限制清晰可复现 |
| 真实模型 | 至少两条实际可用路由完成短任务；记录实际发送参数和工具往返，不以模型自述作证 |

测试分层：纯逻辑单测检查配置与校验；真实宿主加捕获型模型检查路由、生命周期和时序；真实供应商请求检查目标模型、参数和工具调用是否被接受。缺少真实宿主或密钥的 CI 明确显示 skipped，不计入通过。

测试一个供应商的两个模型，不等于已经验证跨供应商。接受一个 effort 参数，也不能证明内部实际消耗了多少推理计算。公开兼容矩阵只能列实际完成的组合。

### 14.1 版本基线

本次查到最新公开 Release 为 **`dsh-v0.1.7-rc.2`，2026-09-24 发布**，且为 prerelease。[S1] 前面讨论中的 alpha.2 不应继续被称为最新版本。

将 rc.2 作为**首发候选测试基线**，不是已验证兼容声明。锁定实际测试的宿主与开发依赖；不要用 master 或未经测试的大范围 `>=0.1.7 <0.2.0` 代替兼容证据。npm 分发标签和 GitHub Release 是两套状态，安装说明从真实打包验收结果生成。

只承诺 DSH Web 的已测组成。不承诺所有桌面内置宿主、CLI、Spaces 或 Editor 立即可用。产品依赖保持通用，平台适配按反馈增加。

### 14.2 一个包，不提前拆 SDK

建议源码结构：

```text
dsh-classmates/
  src/

    bindings.ts       # 不可变实例配置绑定
    tools.ts          # list / spawn

    client.tsx        # 单页列表/编辑

  tests/
  docs/

    compatibility.md
  package.json
  cordis.patch.yml
  README.md
  README.zh-CN.md
```

文件划分可以调整，但首版只有一个发布单元。Host 与 Client 可有各自构建产物，不因此建立四个 npm 包。

依赖应遵循该 DSH 宿主的插件装配规范。特别检查 peer/resolver 是否会自动安装第二份核心，最终以解包后的发布物和干净启动验证，不以开发期 node_modules 成功为依据。[S8]

## 15. 如何尽快获得有价值的反馈

### 15.1 首发演示只展示一个闭环

展示三件事：为两个角色选择不同路由；主控根据明确请求发现并调用角色；成员在官方 Team 内沟通并交付一个小结果。给出脱敏的实际路由证据，展示配置不是只写在卡片上。

不要在演示里搭复杂项目、加跨空间、写长篇小说或宣称通用性能提升。首次展示重点是容易理解、容易复现、容易指出问题。

### 15.2 反馈只围绕四个问题

配置能否完成；主控是否选对角色；实际请求是否符合绑定；跟不用插件相比，结果是否有帮助、过程是否显得多余。

Issue 模板收集宿主精确版本、插件版本、角色定义的脱敏片段、期望/实际路由、最小复现和是否涉及恢复。不要默认索要完整 Session、项目文件或 API Key。插件不新增自动遥测和持续上报。

### 15.3 版本命名和发布文案

建议初次可用包采用 `0.1.0-alpha.1`，强调 experimental，列出已测环境与明确限制。版本号为发布计划，不表示当前已有该包。

可在实现验收完成后使用的文案：

> dsh-classmates 为 DSH 官方 Agent Teams 增加一个用户自定义角色库。你决定每位队友的职责、模型、思考强度和工作指令，主 Agent 根据任务自行调用。插件不规定组队流程，不替换官方消息、任务或会话管理。首版聚焦配置到真实成员的可靠生效。

不使用“全球首个”“最强”“比单 Agent 省一半”等缺乏证据的表达。已有 Team 模型配置和流程插件，越早把差异说清楚，越容易得到对口反馈。[S8][S9]

优先候选是逐角色真实工具限制、导入导出、更多原生客户端入口，以及上游完整 per-teammate composition 支持。它们都不是当前发布门槛。

| 决定 | 理由 | 暂不选择 |
|---|---|---|
| 独立仓库，单 bundle | 与 Editor 解耦，减少发布与依赖成本 | 多包平台、依赖 Editor 私有服务 |
| 主控自行组队 | 用户已明确确认，不重复编排智能 | Recipes、DAG 模板、规则路由器 |
| 两个工具，按需目录 | 避免每角色一个工具和全量长提示 | 工具爆炸、自动注入全部 persona |
| 显式模型绑定 | 首版语义简单，方便验证 | 动态继承、自动 fallback、评分选模 |
| 快照绑定旧实例 | 恢复与重试可解释 | 模板编辑即时改正在运行成员 |
| public model-selection 接入 | 不将上游合入设为首发前提 | 请求末端盲改字段、改全局默认 |
| 官方 Team 始终为运行底座 | 不重复维护状态与协作 | 一次性 subagent 冒充 Team |
| fresh-only | 降低上下文和缓存语义复杂度 | 首发同时支持 fork、共享历史策略 |
| 权限编辑器后置，限制明示 | 不做无法执行的假安全 UI | 提示词冒充沙箱或强制只读 |
| 一个已测宿主组合 | 优先可安装与可复现 | 未测试的宽版本兼容声明 |
