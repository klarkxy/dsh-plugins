# 把知乎接进 DSH：一个插件做了什么，又刻意没做什么

## 缺位的那一层

让模型回答偏中文社区的问题，最容易露怯的往往不是推理，是信源。「这东西值不值得买」「业内怎么看这个问题」——共识沉在知乎，模型却默认够不着：内容锁在站内，公开页面抓不全，开放平台的接口又带着额度和风控。我自己的工作流里，这一段以前是断的：想引一条社区讨论，只能开浏览器搜完，再把摘要手工贴回上下文。检索一断，后面写的全是二手印象。更麻烦的是时效——社区里的结论翻几页就成了旧账，模型复述起来却像最新共识。

`@klarkxy/dsh-zhihu` 补的就是这段路。DSH 是本地运行的 agent 工具链，模型在里面靠工具干活。站点详情页的一句话简介是「知乎搜索、智能体工具、知识库和用量统计」，平铺直叙，却少说了一层定位：它是给模型用的知乎，不面向浏览器前的人。

## 装与配

环境要求 Node ≥22、DSH 0.1.7-rc.2，不用构建本仓库：

```sh
dsh plugin --profile web add @klarkxy/dsh-zhihu
```

重启 DSH Web。Access Secret 来自知乎开放平台，拿到后从「插件」进「知乎」填进去，凭据名是 `ZHIHU_ACCESS_TOKEN`。包名务必写全 `@klarkxy/dsh-zhihu`——不带 scope 的 `dsh-zhihu` 属于另一位维护者，装错了地方，后面排查都会往错方向走。

到这里，插件页的搜索、设置、用量、知识库四个视图都能用了。模型要调工具还差一步：在所用 agent 的 `agent.cordis.yml` 插件列表里加一行：

```yaml
- name: '@klarkxy/dsh-zhihu/tools'
```

## 十二个工具，四层能力

tools 入口启用后，模型手里就有十二个工具。按用途分四层看。

第一层是检索。`zhihu_search` 搜知乎站内；`zhihu_global_search` 走开放平台的全网搜索，检索库可选 `all`（默认）、`realtime`、`static`；`zhihu_hot_list` 拉热榜。三者对应三种颗粒度：具体问题、站外资料、当下社区在聊什么。

第二层是问答与知识库。`zhihu_ask` 直接调知乎直答——OpenAI 兼容接口，基于社区内容生成综合回答，考据和背景调研用它最合适。模型三档可选：默认 `zhida-thinking-1p5` 带思考过程，`zhida-fast-1p5` 快但只适合简单事实查询，`zhida-agent` 最慢也最强，工具描述写明仅在明确要求时使用。`zhihu_knowledge_search` 检索知识库的 RAG 片段，召回范围默认 `public`；在知乎网页端传过个人资料后，可以再加 `personal` 和 `subscription`。

第三层是这次新增的问题发现与创作数据。`zhihu_question_recommendations` 推荐问题：省略 `query` 就按当前账号画像来，给了主题就按主题找。`zhihu_question_answers` 翻问题下的回答。`zhihu_user_content_detail` 和 `zhihu_user_content_comments` 看单条内容的详情与评论，评论排序有 `score`（默认）、`reverse`、`ascending`；评论里附带的子评论不保证给全。`zhihu_creator_account_stats` 与 `zhihu_creator_content_stats` 分别给账号维度和单条内容的创作数据。

这六个连同 `zhihu_quota` 只用当前这把 Access Secret，参数里不暴露密钥，也不做身份切换。链接格式卡得严：问题链接必须是 `https://www.zhihu.com/question/{id}`，内容只认回答、专栏文章、想法和视频；创作数据只查当前账号已发布的内容，视频只返回关联正文。推荐结果不分页，显式传一个空白主题会被直接拒绝。

第四层是用量。`zhihu_quota` 查官方剩余额度；本地另有一套按日计数，记调用次数、失败次数和返回条目数，用量视图默认看 30 天，最多 90 天。业务调用每次只记一条事件，带上额度分类。

代表性工具收在一处，当索引用：

| 工具 | 用途 |
| --- | --- |
| `zhihu_search` | 知乎站内搜索，拉社区证据 |
| `zhihu_global_search` | 开放平台全网搜索 |
| `zhihu_ask` | 知乎直答，基于社区内容的 AI 问答 |
| `zhihu_knowledge_search` | 知识库 RAG 片段检索 |
| `zhihu_question_recommendations` | 按账号画像或给定主题推荐问题 |
| `zhihu_creator_account_stats` | 账号维度的创作数据 |
| `zhihu_quota` | 官方剩余额度查询 |

问题发现、创作数据和官方额度都没有独立的 Web 页面，只能走模型工具和共享 RPC 服务。另外，同一 profile 里如果还装了 `@klarkxy/dsh-web-search-manager`，本插件会注册「知乎全网搜索」后端，通用网络搜索工具也能共用这一把 Access Secret。

## 几处工程取舍

每个检索工具的描述结尾都挂着同一句：「结果仅作社区/读者反馈参考，不构成 canon，也不直接写入项目文件。」初看像套话，但它针对的是模型的真实习性——搜到几条高赞回答，顺手就当成定论写进项目，太容易了。知乎上的内容是讨论，不是裁定。把约束放进工具描述，等于每次调用都提醒一遍：真要沉淀成项目里的结论，得人看过再写。

额度的处理更直白。官方剩余额度只有一个来源：`zhihu_quota` 调 `GET /api/v1/quota`。本地那套按日计数不参与任何推算——不预测余额还剩多少，也不猜什么时候重置。道理不复杂：本地记的是你调了几次、拿回多少条，跟服务端的配额账本没有换算关系，外推出来的数看着像答案，实际是编的。想要真余额，去查额度接口。额度查询本身也不记业务用量，失败了同样不计。

分页是另一个容易做错的地方。规矩只认返回体里的 `paging.canContinue` 和 `nextOffset`，拿到什么就往回传什么：`offset` 是非负 Int64 十进制字符串，默认 `"0"`；`limit` 在 1–50 之间，默认 20。为什么不用条目数推偏移？上游会过滤内容，`Totals` 里可能混着被滤掉的回答，条目数跟偏移对不上。错一页，后面每一页都错：要么原地打转，要么整段漏掉。空页也不代表结束——`nextOffset` 缺失、无效或者没前进，就返回警告停下，绝不硬凑。

错误也一样：所有请求都不自动重试。`30001`、`30002` 是频率或额度限制；`30003` 是风控拒绝，性质不同，工具会明确提示不要立即重试。对限流做退避还算合理，对风控信号继续加压，等于给账号找麻烦。失败原样抛回给模型和用户，下一步由人来定。错误详情还会带上游状态码和建议等待的秒数；超时与取消覆盖到响应正文的读取，不只是请求发出的那一瞬间。

创作数据那边压着几条小规矩：起止日期要么一起给，要么都不给，都不给就用上游默认范围，插件不自己编一段；缺失的指标保持缺失，不补零；比例就是比例，不换算成百分比。正文同样如此——只给上游摘要，缺了就是缺了，不冒充全文；返回的 HTML 在展示时剥掉，放进不会执行的文本块。单看每条都小，合起来是一句话：宁可看起来少一点，也不编一份看似完整的数据。

知识库这边只有一条要提醒：单文件上传上限 20 MB，文件存在知乎云端。别把没发表的手稿传上去。

## 边界在哪

这次对齐上游的范围是问题发现与创作端点，以及官方额度，对应 `zhihu-search` 主库 main 的 `62fd3ce5c5761dd217094280390b394e4eb77ed2`（2026-09-28）。上游 CLI/MCP 的能力没有整批搬过来：OAuth 身份管理、PDF/PPT 任务都还留在那边，插件目前只认当前这一把 Access Secret。所以这条链路的现状是——查知乎、问直答、翻问题、看创作数据都通了；管身份和做文档还没有。等这边真出现需求，再谈移植。
